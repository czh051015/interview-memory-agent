## 架构设计说明


### 一、系统概述

本系统是一个面向申论客观小题的「单题诊断工具」。用户上传一道题的题干、材料、标准答案和自己的作答，系统自动拆解标准答案为采分点列表，逐条判定用户作答的命中情况，输出结构化的诊断报告，并支持用户将题目加入错题本进行间隔重复复习。

**核心设计原则：**
1. **判定可信**：每一条判定都附带证据（材料原文、关键词对比）
2. **用户可控**：用户主动触发深度解析、主动加入错题本
3. **LLM最小化**：只在边界样本和示范生成时使用，降低幻觉风险


### 二、四步处理法则（核心Pipeline）

整个处理流程从用户提交到报告输出，分为四个步骤。


#### Step 1：输入解析与预处理

**输入：**
- 题干（文本）
- 材料（文本）
- 标准答案（文本）
- 用户作答（文本）

**处理逻辑：**
- 标准答案 → 拆解为采分点列表（LLM辅助拆解 + 人工校验，仅在录入时执行一次）
- 每个采分点包含：要点原文、关键词列表、同义表达
- 材料按段落分段，建立索引
- 所有静态资源（题干、材料、采分点、材料索引）存入数据库

**输出：**
- `question_id`（唯一标识）
- `reference_points: List[ReferencePoint]`
- `material_segments: List[MaterialSegment]`
- `user_answer: str`（原始文本）

**执行时机：** 用户上传题目时执行一次，后续复用。


#### Step 2：答案拆解

**输入：**
- `user_answer`（原始文本）

**处理逻辑（纯算法，无LLM）：**
- 按句号、分号、序号（1. 2. ① ②）切分为候选句列表
- 去除语气词、标点符号
- 每个候选句保留位置索引（用于原文高亮标注）

**输出：**
- `sentences: List[Sentence]`
- 每个Sentence包含：`text`（纯净文本）、`original_text`（带标点原文）、`start_pos`、`end_pos`

**执行时机：** 每次用户提交答案时执行。


#### Step 3：采分点比对（核心判定引擎）

**输入：**
- `reference_points: List[ReferencePoint]`
- `sentences: List[Sentence]`

**处理逻辑（三级流水线）：**

**L1 - 硬关键词匹配：**
- 遍历每个采分点的关键词列表
- 若用户句子中直接包含任一关键词 → 判定为「命中」，置信度 0.99，记录命中的具体词
- 否则进入L2

**L2 - 向量相似度：**
- 将用户句子与采分点做Embedding余弦相似度计算
- 相似度 ≥ 0.85 → 判定为「模糊」（意思接近但未用原词），置信度 0.80
- 相似度 ≤ 0.60 → 判定为「缺失」，置信度 0.90
- 0.60 < 相似度 < 0.85 → 进入L3

**L3 - LLM二分类：**
- 仅对边界样本（0.60-0.85）调用LLM
- Prompt限定为二分类选择题："用户句子X与采分点Y在申论阅卷中是否算语义等同？只回答'是'或'否'"
- 回答"是" → 判定为「命中」，置信度 0.70
- 回答"否" → 判定为「模糊」，置信度 0.70

**输出：**
- `hit_detail: List[HitDetail]`
- 每个HitDetail包含：`point`（采分点原文）、`keywords`、`hit_status`（命中/模糊/缺失）、`confidence`、`matched_text`（用户命中的原文片段）、`material_source`（材料段落索引）

**执行时机：** 每次用户提交答案时执行。其中L1+L2为纯算法（无LLM），L3仅在边界样本触发。


#### Step 4：报告组装

**输入：**
- `hit_detail: List[HitDetail]`
- `reference_points: List[ReferencePoint]`
- `material_segments: List[MaterialSegment]`
- `sentences: List[Sentence]`
- `user_answer: str`

**处理逻辑：**
- 计算命中率：命中数/总采分点数
- 对每个「模糊」/「缺失」的采分点，生成逼近引导内容：
  - 材料溯源：从`material_segments`中提取对应段落原文
  - 示范表述：2-3条正确写法（LLM生成）
  - 错因诊断：用户少了哪个关键词、为什么算错
- 对每个「命中」的采分点，标注命中的关键词及位置
- 组装完整报告数据结构

**输出：**
- `report: Report`
- 包含：`hit_count`、`total_count`、`hit_rate`、`hit_details`（带完整引导信息）、`user_answer_annotated`（原文标注版）

**执行时机：** 每次用户提交答案时执行。


### 三、缓存策略

| 缓存对象 | 缓存时机 | 缓存位置 | 有效期 | 命中后行为 |
| :--- | :--- | :--- | :--- | :--- |
| 采分点列表 | 用户上传题目时 | 数据库（question表） | 永久 | 直接复用，不重新拆解 |
| 材料分段索引 | 用户上传题目时 | 数据库（material_segments表） | 永久 | 直接复用，不重新分段 |
| 采分点Embedding | 用户上传题目时 | 数据库（向量字段） | 永久 | 直接用于L2相似度计算 |
| 历史报告 | 每次提交后 | 数据库（report表） | 永久 | 用户重新打开时直接展示 |
| 示范表述 | 首次生成后 | 数据库（hit_detail.suggestion） | 永久 | 复用已有示范，不重新生成 |

**缓存带来的Token节省：**
- 同一道题被多次提交（用户改答案重交）：Step1完全复用（0 Token），只重新执行Step2-Step4
- 边界样本的LLM二分类结果：不缓存（每次提交答案不同，判定可能不同）
- 示范表述：缓存（同一采分点的示范表述不随用户答案变化）


### 四、闭环与结束标准

#### 4.1 闭环结构

```
┌─────────────────────────────────────────────────────────────────────┐
│  用户上传 → 报告 → 决策                                            │
│                     ├── 结束 → 不留存                               │
│                     ├── 加入错题本 → 进入记忆系统 → 定时推送        │
│                     └── 继续追问 → RAG问答 → 结束 → 回到报告        │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.2 结束标准

**健康结束（用户主动结束）：**
1. 用户看完报告后点击「结束」，本次诊断完成
2. 用户点击「加入错题本」，入库后本次诊断完成
3. 用户关掉页面，本次会话自动结束

**不存在的结束：**
- ❌ 强制用户达到100%命中率才能结束
- ❌ 系统自动判定"已掌握"后结束
- ❌ 强制用户看完所有引导内容才能结束

#### 4.3 追问模式

追问模式是RAG问答，独立于报告流程：
- 触发：用户点击「继续追问」
- 上下文：当前题目的`material` + `reference_points` + `user_answer` + `hit_detail`
- 结束：用户点击「结束追问」后回到报告区
- 追问内容不影响报告的判定结果，只作为附加学习材料


### 五、数据流向图（纯文字版）

**方向：自顶向下，单向流动**

1. 用户上传数据 → 存入`RawInput`（题干/材料/标准答案/用户作答）
2. RawInput → Step1（标准答案拆采分点、材料分段） → 存入`ProcessedQuestion`
3. RawInput + ProcessedQuestion → Step2（用户作答分句） → 生成`Sentences`
4. Sentences + ProcessedQuestion.reference_points → Step3（三级判定） → 生成`HitDetail`
5. HitDetail + ProcessedQuestion.material_segments + Sentences → Step4（报告组装） → 生成`Report`
6. Report → 渲染给用户
7. 用户点击「加入错题本」 → Report + ProcessedQuestion + RawInput → 存入`WrongBookItem`
8. WrongBookItem → 进入`mastery.py`调度 → 定时推送


### 六、面试叙事版本

> "我的系统采用四步流水线架构。
>
> **第一步是输入解析**，用户在录入题目时，系统就把标准答案拆成采分点列表、材料分段建立索引，这些静态资源只处理一次，后续复用。
>
> **第二步是答案拆解**，纯算法把用户答案切成候选句，不调LLM。
>
> **第三步是核心判定引擎**，采用三级流水线：硬关键词匹配挡掉60%的确定性情况，向量相似度识别同义替换，只有边界样本才交给LLM做二分类。这样LLM只回答'是/否'，不做开放式判断，极大降低幻觉。
>
> **第四步是报告组装**，把判定结果、材料溯源、示范表述拼装成结构化报告。
>
> 整个流程的结束是用户控制的——他看完报告可以结束、可以追问、可以加入错题本。系统不强迫他做任何事。
>
> 缓存策略也很清晰：采分点列表、材料分段、Embedding向量在录入时缓存，永久复用；示范表述首次生成后缓存；但判定结果每次提交都要重新跑，因为用户的答案变了。"
