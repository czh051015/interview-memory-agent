# 26 · 评分引擎选型与目标取舍决策书（修订：直接 A/B 对比）

> 配套 docs/24（文字解析+Trace）、25（语义匹配层）、benchmark/medium 中间态样本、8 项 eval 回归。
> **修订记录（2026-09-01）**：舍弃"先 A → 再 C → D 评估 → B 不推荐"的渐进路径，改为**直接端到端对比两个引擎**（现有确定性 vs LLM-as-a-Judge），数据说话，谁赢用谁。medium 金标已由用户人工复核通过（nosource 判 0 口径确认）。

---

## 0. 一句话

**不做 A/C/B 渐进，直接对比两个极端：现有的确定性引擎（关键词+语义层）vs LLM-as-a-Judge。** 同一套金标数据，谁在指标上赢就用谁；LLM 不稳就退回确定性；C（材料锚定）只在两者都不理想时才回头做。

## 1. 现状事实（数据层面，非主观）

| # | 事实 | 含义 |
|---|---|---|
| 1 | **dmeta 把「套话 bad 簇」(0.708–0.73) 和「真改写簇」压进同一相似度区间** | 模型能力限制：单靠 dmeta 相似度分不开"泛泛而谈"和"同义改写"——**任何 τ 都在三约束间取舍，这是数据事实不是调参问题** |
| 2 | doc25 目标（fuzzy≤40% + no_fool=1.0 + disc 不恶化）在此模型下**不可达** | 目标与模型能力不匹配，必须取舍 |
| 3 | nosource **零新增命中（13→13，唯一全达标项）** | 语义层没有把 nosource 假阳性搞得更糟（这点达标），但也完全没治它 |
| 4 | 本机仅 dmeta（bge-m3 需另拉 1.2GB，未验证效果） | 换模型有下载成本 + 收益不确定 |
| 5 | τ 候选：0.71（fuzzy 54% 但 disc -9pp、红线余量 0.002）/ 0.734（fuzzy 57%、disc -3.5pp、红线余量 0.026）/ 0.75（fuzzy 68% 几乎白干、disc 保住） | 三条路线的量化代价 |
| 6 | **medium 金标已人工复核通过**（fuzzy 同义酌情全给；nosource 判 0 = 自创/偏题/无可行做法不得分） | 2026-09-01 用户确认，可作为 LLM 评判的 ground truth |

## 2. 为什么单 τ 无解（背景，不再纠结）

**40% 是拍脑袋目标，不是需求**（doc25 的期望值）。真实需求："中间态漏判明显下降、红线不破、区分度不崩"。

| 档位 | fuzzy 漏判 | vs 无语义层（75%） | 红线余量 |
|---|---|---|---|
| 无语义层（现状） | 75% | — | — |
| τ=0.734 折中 | **57%** | **↓18pp，明显改善** | 0.026（稳健） |
| τ=0.71 激进 | 54% | ↓21pp | 0.002（≈失守） |

根因（§1 事实 1）：dmeta 把 bad 簇和真改写簇压在同一相似度区间，**任何 τ 都在这两类之间取舍**——这是 embedding 模型的能力边界，不是调参能解决的。要突破它，只有两条路：换模型（B，收益未知）或换范式（LLM 评判，语义判断交给 LLM）。**直接对比这两条路的代表即可，中间复杂度（C 材料锚定）不做渐进**。

## 3. 为什么舍弃 A/C/B 渐进（本次修订的核心）

| 原路径 | 为什么不做 | 新处理 |
|---|---|---|
| A. 接受 57% 基线 | 只是配置改动，**现有引擎已含语义层**——跑"现有的"就等于跑 A 基线 | 并入"现有的"一侧 |
| B. 换模型 bge-m3 | 1.2GB + 收益未知，且不解决"泛句 vs 改写句"根矛盾 | 不推荐，搁置 |
| C. 材料锚定约束 | **中间复杂度**：如果 LLM 评判直接能治 nosource，C 白做 | 降级为"两者都不理想时"的最后手段 |
| D. LLM-as-a-Judge | 从"评估选项"升级为**对比对象** | 直接和"现有的"对比 |

**逻辑**：与其一步步加复杂度（A→C→D 渐进），不如一次做端到端 A/B——用数据买定答案，避免"中间复杂度陷阱"（每一步都合理，加起来却绕路）。

## 4. 拍板：直接对比两个引擎

| | 现有的（确定性） | 大模型的（LLM-as-a-Judge） |
|---|---|---|
| 判定方式 | 关键词 + 语义层（dmeta + τ=0.734） | LLM 按 rubric 判断 + 强制证据输出 |
| LLM 调用 | 0 | 每题 1 次 |
| 稳定性 | 100% 可复现 | 需验证（重跑一致性 ≥90%） |
| 实现 | 已有（改配置） | 需写 judge_llm.py |

**对比表（同一套 medium + benchmark 金标）**：

| 指标 | 现有的 | 大模型的 |
|---|---|---|
| fuzzy 漏判率 | 57%（τ0.734） | ? |
| nosource 假阳性率 | 100% | ? ← 攻的就是这个 |
| no_fool | 1.0 | ? 必须 1.0 |
| discrimination | 0.864 | ? |
| 重跑一致性 | 100% | ≥90%（生命线） |
| 每次评分成本/速度 | 0 / 秒级 | 贵 / 慢 |

**决策规则（简单）**：
1. **大模型赢**（F1≥0.85、重跑一致性≥90%、no_fool=1.0、nosource 假阳性大幅降）→ 默认引擎切 LLM，确定性引擎留作兜底
2. **大模型不稳**（重跑一致性<90%）→ 退回现有的，再考虑 C（材料锚定）
3. **C 只在两者都不理想时做**（最后手段，不做渐进）

**决策依据**：传感器只要能"可靠指出漏了哪个点"就够支撑练习闭环。用数据一次买定引擎选择，别为传感器的精确度把架构搞到不可维护（教训：早期 mastery 精确算分执念）。

## 6. 实现概要（大致，不含完整代码）

### 6.1 judge_llm.py —— LLM 评判引擎

**入口**（与 score_answer 同签名，方便对比）：
```python
def judge_score(answer, points, materials) -> ScoreResult:
    # 输出 hit/miss 同构；Point.matched_by = "llm"
    # matched_text = 作答支撑句；material_source = 材料支撑句（找不到填空串）
```

**调用**：复用现有 `src/llm.chat_json`（DeepSeek 结构化输出，temperature=0）
**失败兜底**：LLM 挂/超时/pydantic 校验失败 → 降级回 `score_answer`（kw 引擎），评分永不空转

**Prompt（rubric）骨架**：
```
system: 你是申论阅卷人。按采分点逐点判定作答是否得分。
  判定规则：
  - hit   ：作答体现了该采分点（原词或同义改写，意思到位）
  - miss  ：没写 / 写模糊（意思沾边但表达不清）/ 写了但没结合材料（自创/套话/答非所问）
  每个判定必须给证据：
  - matched_text    ：作答里支撑该判定的句子（原句摘录，找不到填空串）
  - material_source ：材料里支撑该判定的句子（找不到填空串 = 未结合材料）
user: 题干 + 材料（截断 ~6000 字）+ 采分点列表(id/point/keywords/score) + 作答全文
输出 JSON: { verdicts: [{ point_id, verdict: "hit"|"miss",
                          cause: "没写"|"写模糊"|"没结合材料"|"",
                          matched_text, material_source }] }
```
校验：pydantic（仿 `decompose_points` 模式），单条失败记 warnings 不整体崩。

**关键设计**：fuzzy/nosource 的区分**全在 prompt 里**（rubric 定义三类 miss 原因），LLM 判定 + 证据强制输出——不需要 τ、不需要分层校准。

### 6.2 对比脚本 compare_engines.py

```
读 benchmark/medium/*.json（金标 expected_hit_ids）+ 对应 benchmark/data 金标
对每条样本跑两个引擎：
  现有：score_answer(text, points)      （kw + 语义层 τ=0.734）
  LLM ：judge_score(text, points, material)
指标：
  fuzzy 样本     → 漏判率（期望给分未判中）+ F1
  nosource 样本  → 假阳性率（判中但金标不该给）
  bad 样本       → no_fool（跑题未被判全命中）
  重跑一致性     → 每条跑 3 次（temp=0），判定一致比例（LLM 特有，生命线）
  成本           → LLM 调用次数 / 耗时
输出 §4 那张对比表（把 ? 填成数）
```

## 8. 决策记录（面试叙事）

| 决策 | 选择 | 理由 |
|---|---|---|
| 路径 | **舍弃渐进，直接现有 vs LLM 对比** | 中间复杂度陷阱；数据一次买定答案 |
| 金标 | medium 7 条人工复核通过（nosource 判 0 口径） | 2026-09-01 用户确认，LLM 评测的 ground truth |
| 目标取舍 | fuzzy 57%（0.734 档）为确定性引擎基线 | dmeta 压簇，40% 不可达是数据事实 |
| 换模型 | 不换（bge-m3 搁置） | 1.2GB + 收益未知 + 不解决根矛盾 |
| LLM 评判 | 作为对比对象而非渐进步骤 | 赢了切引擎（F1/一致性/红线达标），不稳退确定性 |
| 引擎组织 | 可插拔并存，不覆盖 | 兜底 + 对照 + 回滚 |

**面试一句话**："我设了 40% 目标，校准发现 embedding 模型把两类样本压在同一相似度区间（数据事实）。我没有一步步加复杂度（换模型、加锚定约束），而是直接做引擎级 A/B 对比——现有确定性引擎 vs LLM 评判，用 F1/重跑一致性/红线同一套金标选型，赢了切引擎、输了可回滚。知道目标什么时候该调整、对比该怎么做，比死磕一个数字重要。"
