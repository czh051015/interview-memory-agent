# 34 · 开发计划书：评分反馈收敛 ——「疑似没写好」组 + 三要素建议卡（修订 docs/33）

> 定位：docs/33（材料高亮 + 左右分栏）已落地，实测暴露口径边界 → 本计划书做三层收敛：
> ① 把「踩到但空泛」（诊断层 quality_cause）并入「没写好」列表——**单独疑似组，不改传感器 hit/miss 口径**；
> ② 建议卡砍到三要素：**没写好的原因 / 标准答案原文(source_snippet) / 建议的改法(fix)**；
> ③ 两处「原文」分工互补：**左栏材料原句 = 素材定位（仅确定漏点高亮），右栏标准答案原句 = 范本对照（所有点都有）**。
> 本文档**修订 docs/33**：分栏骨架、左栏琥珀高亮+编号、命中折叠、错题本按钮均保留；改动集中在右侧列表分组、建议卡内容、疑似锚移除三块。

## 0. 一句话

评分后右侧列表分两组：「**确定没写好**」（传感器 miss：①没写 ②答非所问 ③自创没结合材料）与「**疑似没写好**」（④ 踩到但空泛/套话，LLM 标注 `quality_cause`，行 tag「可能太空泛，需人工判断」）。点开任一行，建议卡只给三要素——原因（漏因=规则文本比对 0 token / 质量因=LLM 标注）、标准答案原文（官方怎么写）、改法（LLM）。demo（候选改写示例）、疑似锚（fuzzy_source）、讲解（explain）砍出 UI。左栏材料高亮只服务「确定漏点」的素材定位。

## 1. 背景与为什么改（实测 → 口径边界）

- **用户实测**：让 AI 生成「结果较差」的答案（点全踩但空泛）→ 评卷全命中。读码定位两层根因：
  1. docs/29 口径回归把质量维度拆出传感器：judge_llm rubric 第 3 步明确「深度不足/套话 → cause=套话无具体性 作诊断标注，不得改判 miss」（judge_llm.py:54-66）；
  2. **诊断结果被序列化层丢弃**：judge_llm.py:179 已写 `h.quality_cause`，但 practice_submit 的 hits 只发 5 个字段（shenlun.py:169-174），`quality_cause`/`miss_cause` 均未透传 → 前端只见干净的全命中。
- **产品定位**「AI 帮你标注差异，你自己判断要不要补」→ ④ 应该可见，但**不可硬判 miss**（docs/28/29 实证：把深度/没结合材料当漏点判，nosource 假阳曾 100%，口径回归后仍 36%）。
- 用户拍板（2026-09-02 三轮 AskUserQuestion）：④ 写入「没写好」列表但给原因标注「可能太空泛，需人工判断」；建议区只留三要素；左栏材料 vs 三要素标准答案原文分工互补。
- 附带收益：砍 fuzzy_source 后，无材料锚的漏点改用 source_snippet 给范本（不再需要"就近语义弱标"），每次 guidance 省一次云端 bge-m3 调用。

## 3. 目标结构

### 3.1 判定 → 展示映射（核心语义，实现者先读这段）

```
传感器判定（kw 规则 / LLM rubric）      诊断层（LLM rubric 第3步 cause）
   ├─ miss（①没写 ②答非所问 ③没结合材料） → 「确定没写好」列表（琥珀编号，左栏材料高亮）
   ├─ hit 且 quality_cause 为空（⑤）      → 「命中」折叠区
   └─ hit 且 quality_cause 非空（④）      → 「疑似没写好」列表（⚠ 徽标，无编号，不高亮材料）
```

- ④ 在材料上**刻意不高亮**：套话/自创点的材料支撑本就不可靠（LLM 引述或为空），且高亮会暗示"该抄这句"（错误暗示）；它的范本是标准答案原文（D15）。
- 诚实边界：kw 引擎无 ④ 判据（`_score_answer_kw` 不设 quality_cause）→ 疑似组仅在 **LLM 引擎**下出现；kw 只是降级兜底，正常不触发。

### 3.2 右栏列表（docs/33 单组 → 双分组）

```
没写好 · 确定（N）                         ← submit.misses
  ① 就业优先    （琥珀编号 ①，对应左栏材料高亮）
  ③ 公共服务    tag「自创无材料」            ← miss_cause 非"没写"时展示
疑似没写好（N）                            ← submit.hits.filter(h => h.quality_cause)
  ⚠ 民生提质    tag「可能太空泛，需人工判断」  ← 无编号、不高亮材料
命中（N）折叠小字                           ← 保留（docs/33）
```

- 默认选中：确定 miss 的 leading（docs/33 原逻辑）→ 若无确定 miss，选中疑似组第一个（D18）。
- 疑似组**不参与 hit_ratio/passed 计算**（口径不变），只在 UI 分组出现。

### 3.3 建议卡（六件套 → 三要素，docs/33 §3.3 模板修订）

```
建议 · {badge} {point}                    ← badge：编号 / ⚠疑似 / 最该补角标
🔬 没写好的原因：{cause}
     · 确定漏点：规则文本比对（"检测到「X」，未检测到「Y」"，0 token，docs/33 已落地）
     · 疑似组：quality_cause 文本（如"套话无具体性——点了但空泛，需展开"）
📖 标准答案原文：{source_snippet}          ← 官方怎么写（拆点一字摘录），全部点都有
🛠️ 建议的改法：{fix}（供参考，以官方答案为准）← 确定漏点走原 DEMO；疑似组走 quality 分支（§4.3）
[＋ 错题本]                               ← 保留
```

**砍掉的行**：✍️ 候选改写示例（demo）、📄 应抄原话（材料句已左栏高亮，避免重复）、📄 或 材料疑似句（D16）、追问讲解按钮（D17）。

### 4.2 practice_submit 序列化补字段（shenlun.py:169-184）

### 4.3 guidance 增疑似组分支（src/mock/runtime.py + prompts.py）

- 现状：guidance 只服务 miss 点（L4 文本比对 + DEMO_PROMPT"漏了一个采分点"语境）。
- 疑似组点开（D19）：guidance 收到的 point 是 **hit 且带 quality_cause** → 分支：
  - 不再生成"补写漏点"式 demo/fix，改走 **quality 示证**：prompt 语境 = "用户写到了这个点但空泛/套话，示范如何结合材料把这点写具体（展开主体/方式/成效），给一句示范 + 一句回材料抓细节的改法"（新增 `QUALITY_DEMO_PROMPT` 常量，或 DEMO_PROMPT 加条件段）；
  - `cause` 字段填 `quality_cause` 文本（疑似组没有"漏词"比对意义）；
  - `material_source` 不强求（不高亮材料，D15）。
- 判定「该 point 是否疑似组」：guidance 内 `score_answer` 重算结果里该点在 hit_points 且 `quality_cause` 非空 → 走分支；否则原逻辑。（与现 guidance 复用同一 `sr`，只加判断）
- D16：guidance 删除 `_find_fuzzy_source` 调用；`GuidanceResult.fuzzy_source` 字段与 API 下发同步移除（无引用方后清理）。

### 4.4 测试同步

## 8. 决策记录（面试叙事，docs/33 §10 更新版）

> "评分反馈收敛成『漏点传感器 + 质量诊断标注 + 人裁』三层：传感器只判踩点（0 token 规则或 LLM rubric），质量诊断只标不判（quality_cause），两者同屏但**分组呈现**——踩到但空泛的点进『疑似没写好』并标『需人工判断』，因为把深度塞回 miss 会造成 36% 假阳（口径回归实测），AI 不确定的点就明说交给用户。反馈区只留三件事：为什么没写好（漏因是确定性文本比对 0 token，质量因是 LLM 诊断）、官方怎么写（拆点时从标准答案一字摘录的原句）、怎么改（LLM 一句改法）。左栏材料高亮只负责告诉你素材在哪，范本对照在右栏——两处原文分工，不重复。"
