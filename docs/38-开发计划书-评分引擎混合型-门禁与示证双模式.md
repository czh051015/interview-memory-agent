## 0. TL;DR

评分引擎收敛为**双模式**，由「题目是否可信（trusted）」切换：

```
请求带 question_id 且在题库 → 门禁模式（gate）  ：规则定绿/黄，灰色带才让 LLM 说「疑似」，永不硬判
请求内联无 question_id    → 示证模式（align）  ：只标差异不判断（docs/37 配对形态，0 判定 token）
```

- **门禁模式 = 硬性门禁 + 软性标注**：每点 kw 全中出现 → 绿（规则）；全缺 → 黄（规则）；部分出现 → 该点进 LLM 做**疑似标注**（"疑似宽泛/疑似方向偏离/疑似表述不清"，可空；空则放行绿）。
- **LLM 在门禁模式只剩两个无伪造面的职责**：灰色带疑似标注（只输出 label+reason，**无证据字段**）+ 点开后的改进建议（候选措辞）。全链路**没有任何 LLM 生成的"命中证据"字段**——docs/36 查出的"材料顶包"在结构上不可能复现。
- **绿的定义比 docs/35 严**：需要该点**所有 kw 都出现**（不是 any），"只踩一个 kw"进灰色带交 LLM 裁——这同时修复了 docs/35"擦边即 hit"的判太宽问题。
- 第三阶段建议区（仅门禁模式，点开懒加载）：**为什么标**（随评分返回，0 额外调用）+ **标准答案原文**（source_snippet 为空时用材料锚句兜底）+ **改进建议（候选，1 次 LLM）**。
- 示证模式吸收 docs/37：无 trusted 时输出差异配对（未见对应 / 候选相似 / 孤儿句），不做任何"漏没漏"判断。

## 1. 背景与动机（决策链）

| 文档 | 路线 | 结局 |
|---|---|---|
| docs/35（已落地） | 五档徽章：LLM 当判官（verdict+5 种 cause） | 实测暴露**材料顶包**：作答没写的点（c4/c9），LLM 从材料借句判 hit |
| docs/36（未落地） | 给 35 打补丁：prompt 硬约束 + 证据自洽防线 | 用户否——"让 LLM 别犯傻"治标不治本 |
| docs/37（未落地） | 判定层整体退役 → 纯示证配对 | probe_align.py 验证 0 token 能把顶包点标成"未见对应"；但用户不接受丢门禁 |
| **docs/38（本方案）** | **混合型：可信题跑门禁、不可信题降示证** | 规则管确定性两端，LLM 只在灰色带输出"疑似"，永不硬判 |

**为什么这次的结构性安全成立**（写进面试叙事）：docs/35 的顶包根因是"LLM 既当证据生成者又当裁判"。docs/38 把这两个角色**拆开**——证据（命中句/缺失词/材料锚）全部由 0 token 规则生成；LLM 只做两件没有伪造面的事：① 对灰色带输出 label+reason（不产证据字段，reason 只是解释性文本）；② 生成改进建议（"候选/供参考"措辞，本就是建议非事实）。**凡是要当事实展示的东西，全部可回溯到规则。**

## 2. 双模式架构

```
practice_submit 请求
   ├─ question_id 非空 且 _load_or_404 校验在库 且 gold 内容与库题一致（D41）──▶ 门禁模式 gate
   └─ 否则（内联 gold / 无 id）──────────────────────────────────────────▶ 示证模式 align
```

| | 门禁模式（trusted 题） | 示证模式（即录即评题） |
|---|---|---|
| 一句话 | 审过的真题，允许系统说"绿/黄/疑似" | 没审过的题，系统只摆差异 |
| 每点输出 | hit（绿）/ miss（黄）/ suspect（蓝 疑似） | 配对结果：命中 / 未见对应 / 孤儿句 |
| LLM 判定 | 有，但只在灰色带且只标"疑似" | 无（0 判定 token） |
| 材料锚（左栏） | 绿/黄/蓝点都锚「材料第X段：原话」 | 配对到材料句即展示 |
| 改进建议（候选） | 点开懒加载 1 次 LLM | 不提供（判定退役，建议跟着退役） |
| 适用 | SAMPLE 真题、题库推题 | 用户手工贴题/上传 |

**前端必须明示当前模式**（header 角标）：「门禁模式 · 审过题」（绿/黄/蓝徽章可用）vs「示证模式 · 仅标注差异」（无三色判定，只显示配对行）。用户对"为什么这题有判那题没有"的困惑由角标消除。

## 4. 门禁模式详细设计

### 4.1 第一阶段：规则门禁（0 token，对每点独立）

```
对每个点 p（kw = p.keywords，2~5 个）：
   命中数 n = |{kw ∈ p.keywords : kw in answer}|
   n == 全部  → hit（绿 · 关键词）
   n == 0     → miss（黄 · 漏答）
   0 < n < 全部 → 灰色带 → 第二阶段
```

每点确定性证据（规则生成，逐字可复核）：
- hit 绿：`matched_terms` = 命中的 kw 列表；`evidence` = 作答中含 kw 的原句（substring 定位整句，0 token）
- miss 黄：`missing_terms` = 缺失的 kw 列表；reason = "作答中未找到关键词：A/B/C"（候选措辞，用户可复核后自判是否同义改写）
- 两类点的 `anchor` = `_find_material_source(kw, material)`（score.py:155 现成，0 token）

**注意**：本阶段不复用 `_score_answer_kw`（它是 any 命中即 hit 的两段式）。门禁规则是全新的 all/partial/none 三态，纯 kw、无 embedding。embedding 只留在示证档做弱配对（37 §5.3）与（可选）灰色带辅助，不参与门禁判定。

### 4.2 第二阶段：灰色带 LLM 疑似标注（仅灰色带点，一次调用）

**输入构造（关键：不给材料全文，只给该点官方写法）**：
- 灰色带各点：id / 名称 / 官方原句（source_snippet ?? 材料锚句，D46 同源兜底）/ 全部 kw / 命中的 kw
- 作答全文（必要时先规则切句）
- **不含材料全文、不含其他点的答案原文**——LLM 无材料可借，"顶包"输入面直接不存在

**Prompt 草案（实现者照抄）**：

```
系统：你是申论评卷的"存疑标注员"。你的任务不是判对错，而是对"关键词部分命中的
采分点"给出是否存疑的标注。你只标"疑似"，从不判"漏了/错了"。

判定依据只有下面两段输入：
【该点官方写法】（标准答案原句或材料对应句——该点"写到什么程度算够"的基准）
【考生作答】（全文）

对每个点，判断：考生作答是否表达出了官方写法的核心内容？
- 表达出来了（虽未逐词命中，但语义等价的实质展开，或缺失的关键词被同义覆盖）
  → "suspect": null（放行，交给规则层显示为命中）
- 没表达出来或表达不到位：
  → "suspect": {"label": 三选一, "reason": "一句话，写给考生看"}

label 判定参考：
- 疑似宽泛：只写了上位概念/口号/价值，无机制、对象、举措、成效等实质内容
- 疑似方向偏离：写的内容与官方写法指向不同的对象/方面（答非所问的更轻表述）
- 疑似表述不清：内容沾边但笼统含混，说不清具体是什么

硬约束：
- 严禁引用、改写、脑补输入中不存在的句子。判定只依据上述输入。
- 你不需要给"证据句"——证据由系统规则提供。你只给 label 和一句话 reason。
- reason 用口语、面向考生，解释"为什么存疑"。

输出 JSON（只输出 JSON）：
{"verdicts":[
  {"point_id":"c5","point_name":"民生联动","suspect":null},
  {"point_id":"c8","point_name":"民生提质",
   "suspect":{"label":"疑似宽泛","reason":"你只写了'获得感幸福感'的口号，没写共建共享的具体机制"}}
]}
```

**为什么不给证据字段**：docs/36 顶包的伪造载体就是 `matched_text`（LLM 自由写的"命中证据"）。本方案命中证据全由规则定位（4.1），LLM 输出面没有可放伪造句子的槽位——这是比 docs/36"事后自洽校验"更强的**事前结构约束**。

### 4.3 第三阶段：建议区（点开某点懒加载，仅门禁模式）

| 区块 | 内容 | 来源 | token |
|---|---|---|---|
| ① 为什么标 | 绿·关键词：命中 kw 列表；绿·语义：LLM 无存疑放行；黄：缺失 kw 列表 + 候选说明；蓝：LLM reason | **随评分响应返回** | 0 |
| ② 标准答案原文 | source_snippet ?? 材料锚句（D46） | 评分数据 | 0 |
| ③ 改进建议（候选） | gap（差距在哪）/ how（怎么补，结合②的官方写法与材料出处）/ rewrite（示范句：漏答给全新示范，沾边给改写） | guidance 1 次 LLM，措辞带"（供参考，以官方答案为准）" | 1 |

① ② 是纯数据回放（评分响应已含），只有 ③ 需要点开时 1 次调用——与 docs/35 落地态的懒加载节奏一致。

## 6. 接口契约变化

### 请求
```ts

interface InlineGold {
  points: InlinePoint[];
  material: string; question: string; qtype: string;
```

### 响应（practice_submit 返回体重构）
```ts
interface PointVerdict {
  point_id: string; point_name: string;
  mode: "gate" | "align";
  status: "hit" | "miss" | "suspect";        // 示证档无此三值，用 align 字段替代
  matched_by: "kw" | "llm";                  // 规则绿 vs LLM 放行绿（透明可查）
  terms: { matched: string[]; missing: string[] };   // 规则证据，逐字可复核
  evidence: string;                           // 作答原句（规则定位，逐字）
  anchor: string | null;                      // 「材料第X段：'…'」（hit/miss/suspect 都下发）
  official: string;                           // source_snippet ?? anchor 句（D46 兜底）
  suspect: { label: string; reason: string } | null;  // 仅 status=suspect 非空
  reason: string;                             // 为什么标（规则文案或 LLM reason）
}
interface PracticeResult {
  mode: "gate" | "align";
  verdicts: PointVerdict[];                   // 门禁：按 point_order 逐点；示证：align 结构（另行定义，37 §6）
  // 示证档附加：alignments / gaps / orphans（37 §6）
}
```
同时补上 docs/36 查出的老缺口：**hits 的 material_source 一并下发**（序列化层 shenlun.py:169-175 目前 hits 不传 anchor，现在统一走 PointVerdict 字段，一并解决）。

## 10. 给实现者的三个注意（踩坑预警）

1. **`_score_answer_kw` 不要顺手删**：旧评测对照与示证档 kw 配对共用它的切句/锚定工具函数（`_anchor_sentences`/`_find_material_source`），只加不减。
