# 05-重构方案：模拟面试模块化（拆成 `src/mock/` 包）

> 状态：方案文档（待评审，未动手）
> 关联：`run_mock_interview.py`（1032 行单脚本）、`app/api/mock.py`（Web 封装）、`cleaner` 包（对比参照）
> 结论先行：模拟面试**应该**重构成包，但核心收益不在"拆文件"本身，而在**消除写回逻辑的两份实现**。

---

## 1. 为什么重构（动机）

cleaner 是 `src/cleaner/` 正经包（`schema/decompose/annotate/status/state_machine/prompts` 各一文件、各有一套测试）。模拟面试却是：

- `scripts/run_mock_interview.py` —— **1032 行单脚本**，所有生命周期函数堆在一起；
- `app/api/mock.py` —— 316 行 Web 封装，又**重写了一遍写回逻辑**。

这不是"设计使然"，一半是历史包袱：cleaner 是项目第一件做的事（记忆机制层），一开始就按包设计；模拟面试是"后置"的第三层，作为 CLI 脚本起步后从没重构进包。

**最该修的不是"文件大"，而是"写回逻辑重复且不一致"**（见 §3）。拆包只是让这件事可维护、可讲。

### 2.2 写回逻辑：重复且行为不一致（核心问题）

| | CLI（`run_mock_interview.py`） | Web（`app/api/mock.py`） |
|---|---|---|
| 函数 | `_write_back` + `record_result` + `_log_write_back` | `mock_complete`（225–316 行） |
| weak 题涨跌 | `mastery.review/review_fail/review_partial` | 同左（250–249 行） |
| 新题采集 | `_collect_new_item` | 同左（270 行） |
| **feedback 写进 answer？** | **否**（`record_result` 只更新 mastery + 合并 behavior_tags） | **是**（250–256 行：fail/partial 时把 LLM 反馈 `_feedback_text` 追加进 `item.answer`） |
| review_log | `_log_write_back`（只记 weak） | 同左（309–314 行） |

> **关键发现**：两处不是"同一逻辑复制两份"——**Web 会把面试官反馈写进题目 answer 字段，CLI 不写**。抽共享核心时必须先做行为裁决（见 §5），否则"去重"会悄悄改变 CLI 行为。
>
> ⚠️ **"面试反馈"是单题判卷，不是整场评价**（澄清）：这里写的 `feedback` = **单道题**的面试官判卷文本 —— 由 `_feedback_text`（`run_mock_interview.py:503`）把该题 LLM 判定 `{points 期望要点, misses 漏答, reason 评语}` 拼成可读文本，写进**那一道题**的 `item.answer` 字段。它**不是**整场面试评价；整场评价是 `summarize_behaviors`（行为标签）+ `generate_review_report`（逐题复盘 markdown），这两套只返回给人看、**不落 answer 字段**。

## 3. 目标结构（`src/mock/` 包）

对齐 cleaner 的"一阶段一文件 + prompts 独立"模式：

```
src/mock/
├── __init__.py      # 公共 API re-export + 常量(WEAK_POOL_SIZE/MAX_FOLLOWUPS/MAX_TOTAL_QUESTIONS) + _ACTION_OF
├── prompts.py       # 抽出自 inline 的面试 prompt（_BEHAVIOR_PROMPT、plan/judge/followup 的 system prompt）
├── plan.py          # get_weak_questions, _read_doc, _read_profile, plan_interview
├── runtime.py       # decide_next, generate_dynamic_question, interview_one, run_dynamic_session, recover, 进度持久化*
├── judge.py         # get_expected_points, judge_followup, judge_single_round
├── writeback.py     # apply_verdict(共享核心), record_result, _collect_new_item, _feedback_text, _log_write_back
├── report.py        # summarize_behaviors, generate_review_report, _format_review
└── cli.py           # main() + --recover

scripts/run_mock_interview.py   # 降级为薄壳：`from src.mock import *`（保兼容，测试零改动）
app/api/mock.py                 # 改 import src.mock；mock_complete 调 writeback.apply_verdict
```

`*` 进度持久化函数（`_save_progress` 等）与 `recover` 是 CLI 专属的运行态，随 `runtime.py`/`cli.py` 走。

## 4. 三档重构范围（从轻到重）

### Tier A — 必做、价值最高（= Phase 1）
1. **抽 `src/mock/writeback.py`**：把"一次判定 → mastery 涨跌 + 新题采集 + review_log"提成 `apply_verdict(records, behaviors, space)`，CLI 与 Web 共用。**这是整个重构最大的收益**（消 DRY + 统一行为）。
2. **改 `app/api/mock.py`**：`mock_complete` 改调 `writeback.apply_verdict`（删掉 225–316 行的内联实现）。
3. **补 `tests/test_mock_writeback.py`**：锁死共享 `apply_verdict`（这之前是两边各写、最该测的部分）。
4. **不动** `scripts/` 壳、**不碰**其他测试 import（靠壳兼容）。

### Tier B — 结构清晰（= Phase 2）
5. **抽 `prompts.py`**：把脚本里 inline 的面试 prompt 挪出来，对齐 cleaner。
6. **拆模块**：按 §3 把 1032 行拆成 `plan/runtime/judge/report/cli`。
7. **`scripts/run_mock_interview.py` 变薄壳**：`from src.mock import *` 保留 `mi.*` 符号，现有 3 个测试文件零改动。

### Tier C — 收尾清场（= Phase 3）
8. **迁 `eval/mock_interview_eval.py:35`** → `from src.mock.judge import judge_single_round`。
9. **迁 3 个测试文件** import（或直接靠壳保留，无需改）。
10. **迁 `offerloop.py:29`** import。
11. **删 `scripts/run_mock_interview.py` 壳**（若第 9–10 步已完成），更新文档引用（`README.md`、`architecture-spec.md`、`MOCK-INTERVIEW-FRONTEND-DESIGN.md`、`模拟面试最小闭环设计.md` 中提到的 `run_mock_interview.py` 路径）。

## 5. 关键决策点（动手前必须拍板）

**写回时"feedback 是否写进 answer"——以谁为准？**

- 现状：Web 写、CLI 不写。
- 推荐：**以 Web 行为为准**（fail/partial 的 weak 题，把 LLM 反馈 `_feedback_text` 追加进 `item.answer`）。
  - 理由：符合项目"答案对照"价值（见项目记忆——缺答案对照由模拟面试 LLM 补）；用户复盘时有可看的标准答案。
- 后果：CLI 会**新增**"写回 answer"行为（此前没有）。这是本次重构**唯一的行为变更**，需在 Phase 1 单测里显式覆盖，并提醒用户"。

> 若你觉得 CLI 不该写 answer，也可反过来以 CLI 为准、Web 去掉那段——但会丢失"面试官反馈沉淀为答案对照"的能力，不推荐。

**但还有一层更根本的设计抉择（建议一并拍板）：写入「哪个字段」？**

- 当前 Web 是**复用 `answer` 字段**装面试官反馈，而 `answer` 的 schema 定义是"面经自带的参考答案"（`schema.py`）。这等于**语义超载**——一个字段既要装面经标准答案、又要装面试官判卷反馈。
- 更干净的做法：给 `KnowledgeItem` 加**专用字段**（如 `feedback` / `interviewer_notes`），把"面试官判卷反馈"与"参考答案"分开存，`answer` 回归"面经/标准答案"语义。
- 取舍：加字段要动 `schema.py` + 迁移存量数据 + 前端展示；复用 `answer` 改动小但语义混。若本重构只求"去重+统一行为"，可先沿用 `answer` 复用（以 Web 为准），把"加专用字段"列为后续 independent 优化。**默认建议：本重构先用方案 A（复用 answer），不动 schema；专用字段作为单独议题。**

## 6. 实施步骤（建议顺序）

**Phase 1（最小、最值，半天级）**
1. 新建 `src/mock/__init__.py`（先只放常量 + `_ACTION_OF` + 空 re-export 占位）。
2. 新建 `src/mock/writeback.py`，实现 `apply_verdict`：
   - weak 题：`record_result` 涨跌 → 若 fail/partial 追加 `_feedback_text` 到 answer → 收集 updated；
   - 非 weak 且 fail/partial：`_collect_new_item` 收集 new；
   - 返回 `(updated_items, new_items)`；review_log 由调用方在 `store` 成功后调 `_log_write_back`（沿用"写库成功才记日志"约定，避免 `--recover` 重复记）。
3. 改 `app/api/mock.py`：`mock_complete` 调 `apply_verdict`，删内联实现。
4. 补 `tests/test_mock_writeback.py`（mock `mastery`/`store`，断言涨跌、新题采集、answer 追加、review_log 时机）。
5. 跑 `tests/test_mock_api.py` 确认 Web 路径仍绿。

**Phase 2（结构清晰，按需）**
6. 抽 `prompts.py`、拆 `plan/runtime/judge/report/cli`，`scripts` 壳 `from src.mock import *`。
7. 跑 `tests/test_mock_interview.py` + `test_mock_interview_recover.py` 确认壳兼容。

**Phase 3（清场，最后做）**
8. 迁 eval / 测试 / `offerloop.py` / 文档引用 → 删壳。

## 7. 风险与回滚

- **唯一行为风险**：写回 answer（§5）。已用单测覆盖，回滚只需还原 `mock_complete` + 不引入 `writeback.py`。
- **进度/恢复机制**：`recover` 与 `_save_progress` 必须随 `runtime.py`/`cli.py` 完整搬迁，否则崩溃补写失效（测试 `test_mock_interview_recover.py` 会 catch）。
- **壳策略**：Phase 1–2 保留 `scripts` 壳，5 处引用零改动，风险最低；Phase 3 才删壳。
- **numpy/chromadb 本机环境问题**：完整 `pytest tests/` 在本机收集期崩溃（Windows access violation，与本次无关），验证时只跑 mock 相关测试文件即可。
