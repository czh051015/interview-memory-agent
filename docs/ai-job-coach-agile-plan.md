## 1. 愿景与范围

### 1.1 一句话愿景
> 搭建一条 **反馈 → 清洗 → 记忆 → 信号 → 审批 → 评估 → 简报** 的自动化管道：投递求职相关反馈（自己的面试复盘 + 收集的他人面经），系统持续聚类出趋势信号，经产品人（你）每周集中审批后，自动评估其证据强度与可证伪性，最终输出一份项目候选简报（Markdown + JSON）。

### 1.2 "反馈"的定义（决策 Q1/Q8）

| 维度 | 定义 |
| --- | --- |
| 内容边界 | v1 接入两类：**(a) 自己的面试复盘/面经笔记**、**(b) 收集的他人公开面经**；JD/市场信号留 v2 扩 source 枚举 |
| 岗位范围 | **聚焦 AI 应用开发岗**，辅以少量相邻岗（大模型算法/后端）——聚类主题与求职叙事一致 |
| 数据来源 | 手动复制粘贴公开面经（如牛客等平台），不开发爬虫 |
| schema 标识 | `source` 枚举字段区分：`self_review` / `other_jingyan` / 预留 `jd`、`market_signal` |

### 1.3 v1.0 范围边界

**In（v1 覆盖，薄切但全链路）**
- 反馈入箱：CSV 批量导入 + Webhook 实时接入
- 语义清洗：去重、脱敏、标准化（规则 + LLM 双通道）
- 反馈记忆库：Chroma 向量 + metadata 存储与检索
- 信号探测：聚类 + 趋势偏移检测
- 产品人审批：轻量审批闸门（Streamlit，批处理模式）
- 假设评估：证据覆盖度 / 可证伪性打分
- 简报输出：Markdown + JSON，含置信度与有效期
- 工程化：测试、eval 脚本、CI、版本管理、文档

**Out（明确推迟）**
| 项 | 推迟到 | 原因 |
| --- | --- | --- |
| 模拟面试交互 | v3.0 | 依赖记忆库与评估器成熟度，提前做是"为做而做"（决策 Q3） |
| 混合检索 / RRF / Reranker | v2.0 | v1 先建纯向量基线，检索质量 v2 专项提升 |
| 爬虫/自动抓取 | 不做（本期） | 6 周时间盒内的范围风险（决策 Q2） |
| JD/市场信号源 | v2.0 | source 枚举预留扩展位 |
| 多用户 / 权限 | v3.0 | MVP 单人使用 |
| 云部署 / 定时调度 | v2.0 起 | 本地优先，避免环境拖累节奏 |

### 1.4 v1.0 成功标准（MVP Done）
在一条"投放 50 条真实/半真实反馈 → 得到 1 份简报"的端到端演示中跑通，且 §8 全部质量门达标（或按 §8.2 降级流程处理并记录）。

## 2. 版本迭代路线图

敏捷原则：**纵向薄切**——v1 不做单节点的完美，做全链路的贯通；后续版本逐节点加厚。

```
预热期      Sprint0  S1    S2    S3    S4    S5
8/12-16 →  8/17  地基 → 清洗 → 记忆 → 信号 → 审批+评估 → 输出+集成   （v1.0，9/25 发布）
v1.x      ────  bugfix / 指标调优 / 文档打磨（每个 Sprint 评审后视情况插入）
v2.0 增强 ────  混合检索+RRF+Reranker / 审批 UI 升级 / eval 体系扩展 / JD+市场信号源
v3.0 完整 ────  模拟面试交互 / 多用户 / 云部署 / 定时调度
```

### 2.1 蓝图节点 × 版本归属

| 蓝图节点 | v1.0（薄切） | v2.0（增强） | v3.0（完整） |
| --- | --- | --- | --- |
| `inbox` 反馈入箱 | CSV + Webhook | JD/市场信号源扩展 | 多端接入 |
| `cleaner` 语义清洗 | 规则+LLM 双通道 | 清洗策略可配置化 | 自适应清洗 |
| `memory` 反馈记忆库 | Chroma + metadata | 混合检索 + Reranker | 分层记忆（短期/长期） |
| `scout` 信号探测 | 聚类 + 偏移检测 | 簇自动命名优化、漂移报告 | 预测性信号 |
| `approval` 产品人审批 | Streamlit 批处理闸门 | 审批策略与 SLA | 多人协作审批 |
| `evaluator` 假设评估 | 覆盖度 + 可证伪性 | 评估一致性校准（多次投票） | 自动反例搜索 |
| `output` 简报输出 | Markdown + JSON（含置信度/有效期） | 模板化 + 图表 | 订阅推送 |

### 2.2 版本发布规则
- **语义化版本**：`主版本.次版本.修订号`（如 v1.0.0 → v1.1.0 → v2.0.0）
- v1.x：每个 Sprint 评审后可发小版本，只含 bugfix 与指标优化，不加新节点
- v2.0 启动条件：v1 质量门全部达标 + Backlog 中 v2 候选 Story ≥ 3 个
- 每个版本打 Git tag + 更新 CHANGELOG（见 §7）

## 3. 角色与单人敏捷机制

| 角色 | 职责 | 承担者 |

### Sprint 1 · 入箱与清洗（第 2 周）——目标：脏数据变干净

**Sprint Goal**：反馈能进来、能被清洗、清洗可度量。覆盖 US-01 ~ US-06（27 点）。

- [ ] T1.1 US-01：CSV 导入器（校验、ID 生成、错误行隔离）
- [ ] T1.2 US-02：FastAPI `POST /feedback` Webhook
- [ ] T1.3 US-03：去重双通道（规范化哈希粗筛 + 嵌入相似度精判）
- [ ] T1.4 US-04：PII 脱敏（正则 + DeepSeek 识别，白名单校验）
- [ ] T1.5 US-05：标准化（日期 ISO 化、source 枚举校验、文本规范）
- [ ] T1.6 US-06：清洗质量报告 JSON 导出
- [ ] T1.7 eval 脚本：去重准确率 / PII 检出率基线
- [ ] T1.8 **速度复核**：用本 Sprint 实际完成点数重排 S2~S5，必要时触发降级预案（§4）

**决策记录 D1**
| 问题 | 候选 | 选择 | 验证方式 |
| --- | --- | --- | --- |
| 去重方法 | 纯规则哈希 / 纯嵌入 / 双通道 | **双通道**（规则快筛省 token，嵌入兜底语义重复） | seed 12 对重复，准确率 ≥ 95% |
| PII 识别 | 纯正则 / 纯 LLM / 正则+LLM | **正则+LLM**（正则保底，LLM 抓姓名等边界情况） | seed PII 检出率 100% |

**AC**
- **US-03**：Given seed 含 12 对重复，When 清洗，Then 每组仅留 1 条，去重准确率 ≥ 95%
- **US-04**：Given 含手机号/邮箱/姓名文本，When 入库，Then 存储层 0 条 PII 泄漏
- **US-05**：Given 混合格式日期，When 标准化，Then 统一 ISO 输出，0 条因格式失败
- **US-06**：Given 一次清洗，When 完成，Then 报告含去重数/脱敏数/失败数/耗时

**评审演示**：CSV 导入 → 清洗 → 质量报告，现场对比清洗前后。

**决策记录 D3**
| 问题 | 候选 | 选择 | 验证方式 |
| --- | --- | --- | --- |
| 聚类算法 | KMeans / HDBSCAN / LLM 直接分组 | **HDBSCAN**（无需预设簇数，抗噪点；数据量小可承受） | 聚类纯度 ≥ 0.7 |
| 偏移判定 | 固定阈值 / 统计检验 | **固定阈值起步**（v1 可解释优先，统计检验留 v2） | 构造偏移用例可复现触发 |

**AC**
- **US-10**：Given 50 条标注反馈，When 聚类，Then 纯度 ≥ 0.7，每簇有可读中文命名
- **US-11**：Given 人为注入 20 条"AI 面试"新主题反馈，When 重跑，Then 产生偏移告警
- **US-12**：Given 一份信号报告，When 点击证据，Then 可跳回原始反馈条目

**评审演示**：两批数据对比 → 偏移告警 → 证据追溯链。

- [ ] T4.2 US-13：**驳回即归档**，metadata 加 `status` 字段（`approved`/`rejected`/`pending`），支持后续"复活"重审（决策 Q11）
- [ ] T4.3 US-13：**审批不阻塞管道**（决策 Q16）：管道照常运行，简报只输出已审批项，界面展示 `pending_count`

- [ ] T4.5 US-15：可证伪性评估（输出分数 + 反例搜索建议）
- [ ] T4.6 eval：评估一致性基线（同一假设 3 次评估方差）

**决策记录 D4**
| 问题 | 候选 | 选择 | 验证方式 |
| --- | --- | --- | --- |
| 审批交互 | CLI / Web 全栈 / Streamlit | **Streamlit**（单人项目最轻，面试可现场演示） | 审批操作 3 步内完成 |
| 审批节奏 | 实时逐条 / 每周批处理 | **批处理**（待审队列，每周集中审；实时打断对单人是伪需求） | E2E 演示不受审批状态影响 |

**AC**

**评审演示**：完整审批流走一遍（含驳回→复活），展示审批留痕与评估报告。

### 8.2 质量门失败处理（决策 Q15）
不达标**不硬阻塞 Sprint 关闭**，走降级流程：
1. 当 Sprint 内优先加改进任务尝试达标
2. 评审时仍不达标 → 降级阈值，评审记录必须写明：**原阈值 / 新阈值 / 原因 / 偿还计划**（记入技术债）
3. 技术债进入 v1.x Backlog，v2.0 启动前必须清零

> 面试讲法：所有指标都有可复现的 eval 脚本支撑——"这个指标不是我说的，是脚本跑出来的"；降级机制说明我懂"质量门不是教条，是带账本的取舍"。

## 11. 面试讲解要点（电梯陈述）

1. **为什么敏捷**：单人项目更容易范围蔓延，用 Sprint 时间盒 + 版本边界强制收敛
2. **为什么纵向薄切**：v1 全链路贯通优先于单节点完美——先证明"管道有价值"，再投资质量
3. **怎么保证质量**：9 个质量门全部有可复现 eval 脚本，发版前回归；不达标走"降级+技术债"账本而非硬阻塞
4. **怎么做决策**：每个 Sprint 有决策记录（问题→选择→验证），全部 24 项关键决策经 grilling 式追问收敛（附录 D）
5. **版本怎么演进**：v1 薄切 → v2 检索质量（混合检索+RRF+Reranker）→ v3 模拟面试，每个版本有明确启动条件
6. **怎么 dogfooding**：数据聚焦自己的目标岗位（AI 应用开发），简报自己真实使用——"我用自己造的管道发现 XX 信号，调整了投递策略"
