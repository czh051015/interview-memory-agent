## A1 · 线程池

**题**：讲一下 Java 线程池：核心参数有哪些？任务提交后线程池的执行流程是什么？有哪几种拒绝策略？

**要点**：核心参数：corePoolSize、maximumPoolSize、keepAliveTime、workQueue、threadFactory、handler（拒绝策略），以及可选的 allowCoreThreadTimeOut 等；执行流程：核心线程 -> 工作队列 -> 非核心线程（直到 maximumPoolSize）-> 拒绝策略；核心线程用完后先入队而非直接扩容；四种拒绝策略：AbortPolicy（默认，抛异常）、CallerRunsPolicy（调用者线程执行）、DiscardPolicy（静默丢弃）、DiscardOldestPolicy（丢弃队列头部的旧任务）；结合项目实际：比如在异步链路或任务补偿中如何选参、如何选拒绝策略，体现工程权衡；能说出 ThreadPoolExecutor 构造器、execute() 和 submit() 的区别，以及 Executors 工厂方法的坑（如无界队列）

**[good 升级版]** 线程池这块我在之前实习做缓存和异步链路的时候用过，也踩过一些坑，所以对它的参数和执行流程还算比较熟。核心参数有七个：corePoolSize 是常驻核心线程数，即使空闲也不会被回收，除非设置了 allowCoreThreadTimeOut；maximumPoolSize 是最大线程数，包括核心线程和非核心线程的总上限；keepAliveTime 是非核心线程空闲时的存活时间，超过这个时间就会被回收，如果 allowCoreThreadTimeOut 为 true，核心线程也会受这个参数控制；workQueue 是任务队列，用来缓冲来不及处理的任务；threadFactory 是线程工厂，用来创建线程，可以自定义线程名、优先级等；handler 是拒绝策略，当队列满且线程数达到 maximumPoolSize 时触发。还有一个可选的参数是 allowCoreThreadTimeOut，默认 false，如果设为 true，核心线程空闲超过 keepAliveTime 也会被回收，这样可以让线程数在空闲时降到 0，节省资源。

执行流程是这样的：任务提交后，如果当前线程数小于 corePoolSize，就直接创建核心线程执行；如果核心线程满了，任务会先丢到 workQueue 里排队，而不是直接创建新线程，这个顺序很关键，不是一上来就疯狂建线程，而是先让队列缓冲；如果队列也满了，才会创建非核心线程去执行，直到达到 maximumPoolSize；如果线程数已经达到 maximumPoolSize 且队列也满了，就触发拒绝策略。这个流程体现了线程池的设计思想：优先复用已有线程，其次用队列缓冲，最后才考虑扩容，避免资源浪费和系统过载。

拒绝策略有四种：AbortPolicy 是默认的，直接抛 RejectedExecutionException，让调用方感知任务被拒绝；CallerRunsPolicy 是让提交任务的线程自己执行这个任务，相当于把任务回退给调用者，不会丢任务但会阻塞调用线程；DiscardPolicy 是直接静默丢弃，不抛异常也不执行，适合对任务丢失不敏感的场景；DiscardOldestPolicy 是丢弃队列头部的旧任务，然后重新尝试提交新任务，适合允许丢弃旧任务的场景。

结合项目实际，我之前用 RabbitMQ 做消息解耦的时候，消费端线程池就配了 CallerRunsPolicy，因为消息不能丢，宁可让消费线程慢一点也不能丢数据。参数上 corePoolSize 和 maximumPoolSize 是结合了任务量和机器核数来定的，比如机器是 8 核，任务主要是 IO 密集型，corePoolSize 设为 16，maximumPoolSize 设为 32，队列用的有界 ArrayBlockingQueue，容量设了 1000，避免无限堆积把内存打爆。如果队列是无界的，比如 Executors.newFixedThreadPool 默认用的 LinkedBlockingQueue，任务无限堆积会导致内存溢出，而且线程数永远不会超过 corePoolSize，maximumPoolSize 形同虚设。

另外，ThreadPoolExecutor 的构造器有多个重载，最完整的那个有七个参数，我们一般用这个。execute() 和 submit() 的区别是：execute() 提交 Runnable，没有返回值，异常会直接抛给线程池的 UncaughtExceptionHandler；submit() 提交 Callable 或 Runnable，返回 Future 对象，可以通过 Future.get() 获取结果或捕获异常，但异常会被封装在 ExecutionException 里，需要显式处理。我在做异步任务补偿的时候，就用了 submit() 来获取任务执行结果，如果失败就重试。

Executors 工厂方法虽然方便，但有很多坑，比如 newFixedThreadPool 和 newSingleThreadExecutor 用的是无界队列，newCachedThreadPool 的 maximumPoolSize 是 Integer.MAX_VALUE，可能导致创建过多线程。所以实际项目中我都是直接用 ThreadPoolExecutor 手动创建，明确指定参数，这样更可控。

## A2 · 死锁

**题**：多线程编程中如何写一个死锁？死锁的四个必要条件是什么？请写出一段会发生死锁的代码，并说明如何避免死锁。

**要点**：能写出一个多线程死锁的具体代码示例（如两个线程以相反顺序获取两把锁）；准确列出死锁四个必要条件：互斥、持有并等待、不可剥夺、循环等待；能结合自身项目经验说明死锁的排查或避免方法（如锁顺序、超时、tryLock）；体现对并发编程的实际理解，而非仅背诵理论

**[good 升级版]** 我之前在实习的时候，遇到过线上服务卡死的情况，当时排查下来就是死锁。我举个例子，比如有两个线程，一个负责处理订单，一个负责处理库存，它们都需要同时访问订单表和库存表的数据。如果线程A先锁定了订单资源，然后去获取库存资源的锁；而线程B先锁定了库存资源，然后去获取订单资源的锁，这时候如果两个线程同时执行，就会互相等待对方释放锁，谁也拿不到第二个锁，程序就卡住了。我写个简单的代码示例：

```java
public class DeadlockDemo {
    private static final Object lockOrder = new Object();
    private static final Object lockStock = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockOrder) {
                System.out.println("Thread1: locked order");
                try { Thread.sleep(100); } catch (InterruptedException e) {}
                synchronized (lockStock) {
                    System.out.println("Thread1: locked stock");
                }
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (lockStock) {
                System.out.println("Thread2: locked stock");
                try { Thread.sleep(100); } catch (InterruptedException e) {}
                synchronized (lockOrder) {
                    System.out.println("Thread2: locked order");
                }
            }
        });

        t1.start();
        t2.start();
    }
}
```

这个代码里，两个线程分别以相反的顺序获取两把锁，就很容易触发死锁。

死锁的四个必要条件，我记得很清楚：第一是互斥，就是资源同一时刻只能被一个线程占用；第二是持有并等待，就是线程已经持有一个资源，还在等待另一个资源；第三是不可剥夺，就是资源不能被强制从持有者手中抢走，只能由持有者主动释放；第四是循环等待，就是多个线程之间形成一个等待环路，比如A等B，B等A。这四个条件必须同时满足才会发生死锁。

在我那个项目里，我们是怎么避免的呢？首先，我们统一了锁的获取顺序，比如所有操作都先锁订单再锁库存，这样就不会出现相反顺序的竞争。其次，我们用了ReentrantLock的tryLock方法，设置超时时间，如果在一定时间内获取不到锁，就释放已经持有的锁，然后重试或者放弃，这样就不会无限等待下去。另外，我们还用了一些监控工具，比如jstack来查看线程状态，如果发现BLOCKED状态的线程很多，就检查是不是有死锁。

总的来说，死锁的避免核心就是打破四个必要条件中的任意一个，比如通过锁顺序打破循环等待，通过超时打破持有并等待，或者用可中断锁来打破不可剥夺。在实际开发中，我体会最深的就是锁顺序一定要统一，而且尽量缩小锁的范围，减少持锁时间，这样能大大降低死锁的概率。

## A3 · 类加载机制

**题**：Class 文件是如何加载到 JVM 中的？类加载过程分为哪几步？什么是双亲委派模型？

**要点**：类加载过程分为加载、验证、准备、解析、初始化五个阶段，其中解析可在初始化后触发。；加载阶段通过类加载器查找字节码并创建Class对象，双亲委派模型指先委派父加载器加载，父加载器无法加载时才由子加载器加载。；双亲委派模型保证核心类库（如java.lang.String）不被篡改，避免类重复加载，提高安全性。；类加载器分为启动类加载器（Bootstrap）、扩展类加载器（Extension）、应用类加载器（Application），自定义加载器需继承ClassLoader。；结合项目经历说明类加载机制在动态加载插件或热部署中的应用，体现实践理解。

**[good 升级版]** 好的，我来详细讲一下Class文件是如何加载到JVM中的。整个过程分为五个阶段：加载、验证、准备、解析和初始化，其中解析阶段比较特殊，它可以在初始化之后才触发，这是为了支持Java的运行时绑定特性。

首先说加载阶段，这个阶段由类加载器完成，它根据类的全限定名去查找对应的字节码文件，读入内存后创建一个Class对象作为这个类的访问入口。这里有个关键机制叫双亲委派模型，它的核心思想是：当类加载器收到加载请求时，不会自己先去加载，而是先把这个请求委派给父加载器，父加载器再往上委派，直到最顶层的启动类加载器。只有当父加载器反馈自己无法加载时，子加载器才会尝试自己加载。这样做的好处是保证了核心类库的安全，比如java.lang.String，它只能由启动类加载器加载，这样就不会被用户自定义的类所篡改，同时也避免了同一个类被不同加载器重复加载的问题。

接下来是验证阶段，这一步主要是检查字节码的格式和安全性，防止恶意代码破坏JVM。然后是准备阶段，这个阶段会为类的静态变量分配内存，并设置默认值，比如int类型默认是0，对象引用默认是null。接着是解析阶段，把常量池中的符号引用替换为直接引用，比如把类名和方法名的符号引用转换为实际的内存地址。这个阶段可以在初始化之后进行，因为有些引用需要等到运行时才能确定。最后是初始化阶段，执行静态代码块和静态变量的赋值操作，这是类加载的最后一个步骤。

关于类加载器，JVM内置了三种：启动类加载器（Bootstrap）负责加载JDK核心类库，比如rt.jar；扩展类加载器（Extension）负责加载扩展目录下的类；应用类加载器（Application）负责加载classpath下的类。如果需要自定义类加载器，可以继承ClassLoader并重写findClass方法。

我在之前的项目里就用到过这个机制，比如我们做一个Agent系统，需要动态加载一些插件类。当时我们自定义了一个类加载器，每个插件使用独立的类加载器加载，这样插件之间的类就相互隔离，即使它们依赖了不同版本的同一个库也不会冲突。同时，我们通过这个机制实现了热部署，当插件更新时，只需要创建一个新的类加载器去加载新的版本，然后替换掉旧的引用就可以了，不需要重启整个应用。这个实践让我对类加载机制有了更深入的理解。

## A8 · RAG 评估

**题**：如何评估一个 RAG 系统的检索质量？'文档级召回率接近 99%'、'页面级召回率约 77%' 这两个指标分别是怎么定义的？怎么测量？

**要点**：明确区分文档级与页面级召回率的定义：文档级=至少命中一个块的文档数/总文档数，页面级=至少命中一个块的页面数/总页面数；说明测量方式：构建带标注的评估集（如按文档/页面组织查询-答案对），检索后对每个查询判断是否命中对应文档/页面；解释为什么文档级远高于页面级：文档级只需命中任一相关块，页面级要求命中特定页面，粒度更细、约束更强；说明实际测量中的挑战：标注成本、查询多样性、块切分对命中率的影响，以及如何保证评估集代表性；结合项目经验：提到在知识库平台中如何落地该评估体系，如构建查询集、人工标注、迭代优化

**[good 升级版]** 我们当时在知识库平台上搭了一套完整的评估体系，专门用来衡量RAG系统的检索质量。先明确一下这两个指标的定义：文档级召回率，指的是在评估集里，对于每个查询，只要检索结果中命中了该文档的任意一个块，就算这个文档被成功召回，然后统计所有查询中这个比例，我们做到了接近99%。页面级召回率就严格多了，它要求命中的块必须属于我们预先标注的那个目标页面，比如某个PDF的某一页，或者某个Word文档的某一节，这样才算命中，我们做到77%左右。

测量方式上，我们构建了一个带标注的评估集，大概一万多个查询，每个查询都人工标注了对应的目标文档和目标页面，确保覆盖不同业务场景和查询类型。测量的时候，我们跑一遍完整的检索流程，对每个查询判断检索结果里有没有命中对应文档或对应页面，最后分别计算比例。这个过程中，我们特别关注了块切分的影响，比如有些文档块切得比较粗，一个块跨了多页，那页面级命中率就会受影响，所以我们也在迭代优化切分策略。

为什么文档级远高于页面级呢？因为文档级只要命中文档里任何一个相关块就算成功，容错性很强，哪怕检索结果里混入了一些不相关的块，只要有一个对的就行。但页面级要求精确到页，约束更强，比如用户问的是某个合同里的付款条款，文档级可能命中合同其他页的摘要块就算成功，但页面级必须命中付款条款所在的那一页，难度就上去了。所以77%这个数字其实说明我们的检索精度还有提升空间，比如优化向量索引、调整重排序策略，或者改进块切分粒度。

实际测量中挑战也不少。首先是标注成本，一万多个查询的人工标注花了我们团队好几周时间，而且还得保证标注一致性，避免不同人标准不一。其次是查询多样性，如果评估集里都是简单直接的问题，指标会虚高，所以我们特意加入了模糊查询、多跳查询这些难例。另外，块切分对命中率影响很大，比如PDF扫描件转出来的文本可能乱序，导致页面归属不准，我们后来加了版面分析来修正。

结合项目经验，我们落地这套评估体系后，发现它帮我们定位了不少问题。比如有一次页面级召回率突然下降，排查后发现是新增的文档类型切分策略不对，导致很多页面被合并成一个块，后来我们针对不同文档类型定制了切分规则，页面级召回率从77%提升到了82%。这套评估体系也成了我们每次迭代的必备环节，新模型或新策略上线前，都会先跑一遍这两个指标，确保不劣化。
