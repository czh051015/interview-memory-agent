## A1 · 线程池（weak）

**题**：讲一下 Java 线程池：核心参数有哪些？任务提交后线程池的执行流程是什么？有哪几种拒绝策略？

**要点**：核心参数：corePoolSize、maximumPoolSize、keepAliveTime、workQueue、threadFactory、handler（拒绝策略），以及可选的 allowCoreThreadTimeOut 等；执行流程：核心线程 -> 工作队列 -> 非核心线程（直到 maximumPoolSize）-> 拒绝策略；核心线程用完后先入队而非直接扩容；四种拒绝策略：AbortPolicy（默认，抛异常）、CallerRunsPolicy（调用者线程执行）、DiscardPolicy（静默丢弃）、DiscardOldestPolicy（丢弃队列头部的旧任务）；结合项目实际：比如在异步链路或任务补偿中如何选参、如何选拒绝策略，体现工程权衡；能说出 ThreadPoolExecutor 构造器、execute() 和 submit() 的区别，以及 Executors 工厂方法的坑（如无界队列）

**[good]** 线程池这块我在之前实习做缓存和异步链路的时候用过。核心参数的话，corePoolSize 是常驻核心线程数，maximumPoolSize 是最大线程数，keepAliveTime 是空闲线程存活时间，workQueue 是任务队列，threadFactory 用来创建线程，handler 是拒绝策略。执行流程是这样的：任务提交后，如果当前线程数小于 corePoolSize，就直接创建核心线程执行；如果核心线程满了，任务会先丢到 workQueue 里排队；队列也满了，才会创建非核心线程去执行，直到达到 maximumPoolSize；再满了就触发拒绝策略。这个顺序很关键，不是一上来就疯狂建线程，而是先让队列缓冲。拒绝策略有四种：AbortPolicy 是默认的，直接抛 RejectedExecutionException；CallerRunsPolicy 是让提交任务的线程自己跑这个任务；DiscardPolicy 是直接丢掉；DiscardOldestPolicy 是把队列里最老的任务丢掉再尝试提交。我当时用 RabbitMQ 做解耦的时候，消费端线程池就配了 CallerRunsPolicy，因为不想丢任务，宁可让消费线程慢一点也不能丢数据。参数上 corePoolSize 和 maximumPoolSize 是结合了任务量和机器核数来定的，队列用的有界队列，避免无限堆积把内存打爆。

判定：\_\_ok\_\_

**[confident]** 线程池的核心参数是 corePoolSize、maximumPoolSize、keepAliveTime、workQueue、threadFactory 和拒绝策略。执行流程是这样的：任务提交后，先判断当前线程数，如果小于 corePoolSize 就创建核心线程执行；如果大于 corePoolSize，就直接创建非核心线程去执行，直到达到 maximumPoolSize，然后再把多余的任务放到 workQueue 里排队；如果队列也满了，就触发拒绝策略。这个流程要注意的是，线程池是优先扩线程而不是优先入队，这样能保证任务被尽快执行。拒绝策略有四种：AbortPolicy 抛异常、CallerRunsPolicy 让调用者执行、DiscardPolicy 丢弃、DiscardOldestPolicy 丢弃最老的。我之前在项目里用线程池处理异步任务，都是把 corePoolSize 设得比较小，然后队列设得很大，这样既能快速响应又不会耗尽线程。

判定：\_ok\_\_\_

## A2 · 死锁（weak）

**题**：多线程编程中如何写一个死锁？死锁的四个必要条件是什么？请写出一段会发生死锁的代码，并说明如何避免死锁。

**要点**：能写出一个多线程死锁的具体代码示例（如两个线程以相反顺序获取两把锁）；准确列出死锁四个必要条件：互斥、持有并等待、不可剥夺、循环等待；能结合自身项目经验说明死锁的排查或避免方法（如锁顺序、超时、tryLock）；体现对并发编程的实际理解，而非仅背诵理论

**[good]** 我之前在Java实习时处理过一个线上服务，当时用ReentrantLock做资源同步，有一次两个线程同时操作订单和库存，一个先锁订单再锁库存，另一个反过来，结果在高并发下就卡死了。当时我写了个类似这样的代码：线程A锁定lockA然后尝试lockB，线程B锁定lockB然后尝试lockA，如果两边都没释放就会互相等待。死锁的四个必要条件嘛，就是互斥、持有并等待、不可剥夺、循环等待。避免的话，我后来在项目里统一了锁的获取顺序，比如所有操作都先锁订单再锁库存，另外也用了tryLock加超时，获取不到就释放已有的锁，这样就不会死循环等待了。

判定：\_ok\_\_\_

**[confident]** 死锁很常见，我写过很多。比如两个线程分别锁住不同的对象，然后互相等待对方释放，就会死锁。四个条件是互斥、持有并等待、不可剥夺、循环等待。避免死锁最好的办法就是用synchronized，因为synchronized是自动管理锁的，不会产生死锁。我在项目里都是用synchronized，所以从没遇到过死锁问题。

判定：\_\_\_ok\_

## A3 · 类加载机制（weak）

**题**：Class 文件是如何加载到 JVM 中的？类加载过程分为哪几步？什么是双亲委派模型？

**要点**：类加载过程分为加载、验证、准备、解析、初始化五个阶段，其中解析可在初始化后触发。；加载阶段通过类加载器查找字节码并创建Class对象，双亲委派模型指先委派父加载器加载，父加载器无法加载时才由子加载器加载。；双亲委派模型保证核心类库（如java.lang.String）不被篡改，避免类重复加载，提高安全性。；类加载器分为启动类加载器（Bootstrap）、扩展类加载器（Extension）、应用类加载器（Application），自定义加载器需继承ClassLoader。；结合项目经历说明类加载机制在动态加载插件或热部署中的应用，体现实践理解。

**[good]** 类加载到JVM主要分三步：加载、连接和初始化，其中连接又细分为验证、准备和解析。加载阶段，类加载器根据全限定名找到字节码文件，读入内存并生成Class对象；验证是检查字节码安全性，准备是为静态变量分配内存并设置默认值，解析是把符号引用替换为直接引用，这个阶段可能延迟到初始化之后。初始化阶段执行静态代码块和静态变量赋值。整个过程遵循双亲委派模型，就是每个加载器收到加载请求时，先让父加载器尝试加载，父加载器加载不了才自己加载。比如我之前的Agent项目里，我们动态加载一些插件类，就自定义了类加载器，保证插件类和主程序的类隔离，避免版本冲突。我记得在Java里，Bootstrap负责rt.jar，Extension负责扩展目录，Application负责classpath，自定义的话继承ClassLoader重写findClass就行。

判定：\_\_ok\_\_

**[confident]** 类加载过程分为加载、验证、准备、解析和初始化五步，其中验证、准备、解析统称为连接，但解析在初始化之后执行。加载阶段，类加载器从文件系统或网络中读取字节码，验证检查字节码格式，准备阶段为静态变量分配内存并赋初值，解析把符号引用替换为直接引用。初始化执行静态代码块。双亲委派模型是指，类加载请求先由子加载器处理，子加载器无法加载时才委派给父加载器。比如Bootstrap加载器负责rt.jar，Extension负责扩展目录，Application负责classpath。我在之前做Java开发时，用过自定义类加载器来热部署，就是重写loadClass方法，打破双亲委派，直接加载最新的class文件，这样就能更新代码而不用重启JVM。

判定：\_ok\_\_\_

## A4 · Agent 记忆（weak）

**题**：Agent 的短期记忆和长期记忆分别是怎么实现的？分别适用于什么场景？两者如何配合？

**要点**：短期记忆通常用会话上下文窗口或对话历史实现，适用于单轮/多轮对话中的即时信息处理；长期记忆通常用外部存储（如向量数据库、数据库）持久化用户偏好或事实，适用于跨会话的个性化；两者配合：短期记忆提供即时上下文，长期记忆在需要时被检索注入短期上下文；结合候选人经历：提及在Agent Runtime中实现的上下文管理、Compaction或Checkpoint，体现实践；指出实现中的权衡，如上下文窗口限制、检索开销、记忆更新策略

**[good]** 短期记忆我一般理解成当前会话里的上下文，就是对话历史或者Agent执行过程中的状态。在实现上，短期记忆可以就是存在内存里，像列表或者消息数组，每次调用模型时把最近几轮拼进去。但它有窗口限制，所以我会做截断或者压缩，比如我做过一个Coding Agent Runtime，用了Append-only Session Tree和Compaction，就是把历史消息压缩成摘要，减少token消耗，同时保留关键信息。长期记忆呢，是用来跨会话保存用户偏好、事实或者历史结果，我通常会存到外部存储，比如向量数据库或者PostgreSQL，然后需要的时候做检索。比如在知识库RAG项目里，用户的历史查询和反馈可以存起来，下次检索时通过相似度召回，注入到上下文里。两者配合的话，短期记忆负责当前任务的流畅性，长期记忆负责个性化或者知识补充。举个例子，用户问了一个问题，短期记忆里有刚才的对话，长期记忆里存了他之前偏好的文档类型，我会先检索长期记忆，把相关内容加进短期上下文，再生成回答。这样既保证了即时性，又有持久性。

判定：\_ok\_\_

**[confident]** 短期记忆和长期记忆在Agent里其实是一样的，都是存在上下文窗口里。短期记忆就是当前对话的token，长期记忆就是通过微调模型，把重要的信息编码进模型参数里。这样模型就能记住用户的长期偏好。短期记忆场景就是多轮对话，长期记忆场景就是跨会话的个性化。配合的话，长期记忆通过微调隐式影响短期记忆的生成。我在做Agent Runtime时，就是靠微调来让模型记住用户的代码风格，效果很好。

判定：\_ok\_\_\_

## A6 · 代码搜索（weak）

**题**：基于关键词的命令行代码搜索与基于 Embedding/RAG 的代码搜索，各有什么优缺点？各自适用什么场景？

**要点**：关键词搜索：精确、可解释、快、成本低，但无法处理同义/语义/模糊查询，依赖关键词命中；Embedding/RAG搜索：语义理解好、能处理自然语言和同义改写，但需要索引/向量库、延迟和成本更高，结果可能不精确；关键词搜索适合：已知标识符/API名/错误信息/精确代码片段，快速定位；Embedding/RAG适合：自然语言描述意图、跨语言/同义、模糊记忆，但需重排保证精度；结合场景：可混合使用（如先关键词过滤再语义重排），实际项目中需权衡成本、延迟和准确率

**[good]** 我之前在AI Coding Agent里做过代码搜索，两者都用过。关键词搜索就是基于词法匹配，像grep或者用索引，它的优点是快、成本低，结果可解释，搜API名、函数名或者错误信息特别准，因为代码里标识符就是精确的。但缺点也很明显，搜不了语义，比如你搜'怎么实现用户登录'，它根本匹配不到login函数，除非你加一堆同义词。所以它适合已知精确token的场景，比如调试时找某个变量定义。Embedding/RAG就不一样，它能理解自然语言，比如搜'处理用户认证的逻辑'，它能通过向量相似度召回相关代码块，不需要精确关键词。我们当时在RAG平台里用bge-m3做dense检索，配合BM25，就是为了互补。但它的缺点是要建索引、存向量库，延迟和成本高，而且结果可能不精确，容易召回不相关的代码，所以必须加Rerank。适用场景上，关键词适合快速定位已知代码，RAG适合自然语言描述意图，比如让Agent根据需求找代码。实际中我倾向混合，先BM25过滤再语义重排，这样能平衡精度和性能。

判定：\_ok\_\_\_

**[confident]** 关键词搜索和Embedding搜索本质上是互补的，但关键词搜索其实更可靠。因为代码搜索的核心是精确性，比如你搜一个函数名，关键词直接命中，而Embedding可能会返回一堆语义相似但完全无关的结果。所以我认为关键词搜索适用于所有代码搜索场景，尤其是大型代码库，因为它的延迟低、成本低，而且代码本身就是结构化的，不需要语义理解。Embedding/RAG只适合自然语言文档搜索，比如搜需求文档，因为它处理不好代码的精确性。我在项目里就只用关键词搜索，效果很好，RAG那套对代码没什么用，还浪费资源。

判定：\_\_\_ok\_

## A7 · 上下文压缩（weak）

**题**：长时间编程任务很容易超出模型上下文窗口，你采用了什么上下文压缩机制？压缩之后如何维持多轮任务的记忆和执行效率？

**要点**：基于 Append-only Session Tree 进行上下文管理，通过 Compaction 压缩历史消息，保留关键信息。；使用 Checkpoint 持久化压缩后的状态，支持中断恢复和 Fork/Rewind。；压缩后通过摘要或结构化记忆维持多轮任务语义，不丢失关键约束和用户意图。；通过 Provider-Session 绑定和协议适配，确保压缩后消息格式兼容不同模型。；量化压缩效果，如成本降低和任务完成率，验证压缩不影响执行效率。

**[good]** 嗯，这个我在做 AI Coding Agent Runtime 的时候遇到过。我们当时是六轮长会话，模型上下文窗口不够用，所以设计了一套上下文压缩机制。核心是 Append-only Session Tree，就是每次交互都追加节点，不修改历史，然后定期做 Compaction。Compaction 的时候，我们会把早期的消息摘要化，比如把用户最初的仓库描述、目标要求压缩成一段精炼的摘要，保留关键指令和上下文，同时把工具调用的详细参数压缩成结果摘要。这样既能减少 token，又不丢失核心信息。压缩之后，我们用 Checkpoint 把当前会话状态持久化到 PostgreSQL，包括压缩后的上下文、执行到哪一步、中断点在哪。这样如果任务中断或者需要回退，可以 Fork 或者 Rewind 到之前的 Checkpoint。为了维持多轮任务记忆，我们还会把一些长期记忆，比如用户偏好、项目关键决策，结构化存储，在压缩时保留这些。同时，我们做了 Provider-Session 绑定，确保压缩后的消息格式兼容不同模型，比如 Anthropic 和 OpenAI 的接口。最后，我们做了评测，对比压缩和未压缩，P50 成本降低了 56.44%，而且第 2-3 轮的回改成本也回落了，说明压缩没有牺牲任务完成效率。

判定：\_ok\_\_\_

**[confident]** 我们用的是基于摘要的上下文压缩，就是每轮对话后，我们把整个对话历史用 LLM 生成一个摘要，然后只保留摘要和最近的几轮。这样上下文窗口就不会爆。压缩后，我们依赖摘要来维持多轮记忆，但摘要可能会丢失一些细节，所以我们还会把关键信息存到外部数据库，比如用户意图和任务状态。我们做了量化，压缩后成本降低了 50%，而且任务完成率没有下降。我们还用了 Checkpoint 来保存状态，支持中断恢复。总之，我们的方案很有效，适合长任务。

判定：\_\_\_\_

## A8 · RAG 评估（weak）

**题**：如何评估一个 RAG 系统的检索质量？'文档级召回率接近 99%'、'页面级召回率约 77%' 这两个指标分别是怎么定义的？怎么测量？

**要点**：明确区分文档级与页面级召回率的定义：文档级=至少命中一个块的文档数/总文档数，页面级=至少命中一个块的页面数/总页面数；说明测量方式：构建带标注的评估集（如按文档/页面组织查询-答案对），检索后对每个查询判断是否命中对应文档/页面；解释为什么文档级远高于页面级：文档级只需命中任一相关块，页面级要求命中特定页面，粒度更细、约束更强；说明实际测量中的挑战：标注成本、查询多样性、块切分对命中率的影响，以及如何保证评估集代表性；结合项目经验：提到在知识库平台中如何落地该评估体系，如构建查询集、人工标注、迭代优化

**[good]** 我们当时在知识库平台上搭了一套评估体系。文档级召回率呢，就是看每个查询，只要检索结果里命中了这个文档的任何一个块，就算这个文档被召回了，然后统计所有测试查询里这个比例，我们做到接近99%。页面级就严格多了，它要求命中的块必须属于我们标注的那个目标页面，比如某个PDF的某一页，这样才算命中。我们测试集是人工构造的，大概一万多个查询，每个查询都标注了对应用户意图的文档和页面。测量的时候，我们跑一遍检索流程，然后对每个查询判断有没有命中对应文档或对应页面，最后算比例。文档级高是因为只要一个文档里任意一个块相关就能命中，但页面级要求精确到页，所以77%已经很不错了，说明在块切分和检索精度上还有提升空间。

判定：\_ok\_\_\_

**[confident]** 这两个指标其实很简单。文档级召回率是指检索结果中返回的文档数量占知识库总文档数的比例，接近99%说明我们几乎把整个库都检索出来了。页面级召回率是指返回的页面数占总页面数的比例，77%说明我们只检索了四分之三的页面。我们测量的时候，就是跑一遍检索，然后统计返回的文档数和页面数，除以总数。这个定义在业界是通用的，我们当时就是这么算的。

判定：\_ok\_\_\_

## B1 · 项目深挖 · Provider-Session（resume）

**题**：在 AI Coding Agent Runtime 项目中，你设计了 Provider-Session 显式绑定与统一协议适配层。请解释：什么是 Provider-Session 显式绑定？它解决了什么问题？为什么不直接用全局 Session？

**要点**：明确说明 Provider-Session 显式绑定是指每个会话（Session）在创建时显式绑定到一个特定的 Provider（如 Anthropic、OpenAI、Ollama），并在会话生命周期内保持不变。；指出它解决的问题：多 Provider 场景下会话与 Provider 的对应关系明确，避免模型切换导致上下文不一致、工具调用协议差异、成本归属混乱等问题。；解释为什么不直接用全局 Session：全局 Session 会导致多用户/多任务共用上下文，引发安全隔离问题、上下文污染、无法独立追踪和计费，且难以支持多 Agent 并行。；结合项目细节：提及统一协议适配层如何屏蔽 Provider 差异，以及显式绑定如何与 Session Tree、Checkpoint 等机制协同，保证恢复时绑定不变。；提及权衡或边界：显式绑定增加了配置复杂度，但换来了可控性和可观测性，适合多租户或企业级场景。

**[good]** 我们在 AI Coding Agent Runtime 里设计 Provider-Session 显式绑定，简单说就是每个 Session 在创建的时候必须指定一个 Provider，比如 Anthropic 或 OpenAI，而且这个绑定在整个生命周期里不会变。为什么要这么做呢？因为我们的 Runtime 要兼容四种不同的 API，每个 Provider 的上下文格式、工具调用协议、甚至计费方式都不一样。如果不绑定，Session 在执行到一半可能突然换到另一个 Provider，那上下文就得重新适配，工具调用也可能失效，追踪成本归属也乱套了。用全局 Session 更不行，那相当于所有任务共享一个上下文，安全隔离没了，用户 A 的任务可能看到用户 B 的代码，而且没法做独立的 Checkpoint 和恢复。我们的实现里，Session 创建时绑定 Provider，然后统一协议适配层把不同 API 的请求和响应都转成我们内部的统一消息模型，这样 Agent Loop 就不用关心底层是哪个 Provider。另外，这个绑定和我们的 Session Tree、Checkpoint 机制是配套的，因为恢复执行时如果 Provider 变了，Checkpoint 里的状态可能就不兼容了。当然，显式绑定也带来一些限制，比如不能动态切换 Provider，但对我们这种企业级场景，可控性更重要。

判定：\_ok\_\_\_

**[confident]** Provider-Session 显式绑定，其实就是把 Session 和 Provider 做一个映射，每个 Session 可以随时切换 Provider，这样灵活性更高。比如用户先用 OpenAI，再切到 Anthropic，我们通过统一协议适配层自动转换，这样成本最优。全局 Session 的问题在于它没法扩展，因为所有请求都走一个 Session，并发一高就崩了。所以我们的设计是每个 Session 可以绑定多个 Provider，按需切换，这样既保证了兼容性，又提高了系统的吞吐量。

判定：\_ok\_\_\_

## B2 · 项目深挖 · Hierarchy Chunking（resume）

**题**：在 Agentic RAG 平台中，你设计了 Root + Leaf Hierarchy Chunking 与 Leaf-only 检索架构。为什么只把 Leaf 叶子块写入向量库？检索命中后如何回填章节及页面级上下文？

**要点**：Leaf-only 写入向量库的核心动机：避免父块语义冗余和检索噪声，提升向量检索精度与效率；Root + Leaf 层级切分策略：Leaf 是细粒度语义单元，Root 是章节/页面级聚合容器，两者通过元数据或 ID 关联；检索命中 Leaf 后回填上下文：从 PostgreSQL/Redis 中按关联键拉取 Root 块（章节）及页面级元数据，拼接为完整上下文；回填机制保障回答质量：LLM 获得精准证据（Leaf）与全局结构（Root），兼顾答案准确性与可追溯性；权衡说明：Leaf-only 减少向量库体积与检索延迟，但需设计可靠的索引映射与回填查询，避免上下文缺失

**[good]** 我们当时做企业知识库，文档特别长，一个 PDF 可能几十页，如果直接切大块，向量化后语义太混，检索出来经常答非所问。所以设计了 Root + Leaf 两级切分：Leaf 是更细的语义块，比如一个段落或者一个表格，Root 是章节或者页面级别的聚合。只把 Leaf 写进 Milvus，是因为 Leaf 粒度小，向量能更精准地表达局部语义，检索时命中率更高，而且向量库的体量也小很多，索引和查询都快。Root 块就放 PostgreSQL 和 Redis 里，通过一个 chunk_id 和 parent_id 的映射关联起来。检索的时候，先拿 query 在 Milvus 里召回 Top-K 个 Leaf，然后根据这些 Leaf 的 parent_id 去 PostgreSQL 里把对应的 Root 块取出来。取出来之后，我会把 Root 的章节标题、页面信息，还有 Leaf 本身的内容，一起拼成一个上下文窗口，再喂给 LLM。这样 LLM 既能拿到精确的细节证据，又能看到它属于哪个章节，回答的时候更有结构，也方便用户追溯来源。当时我们还测过，这个方案比直接把大块写进向量库，文档级召回率能到 99%，页面级 77% 左右，效果还是很明显的。

判定：\_ok\_\_\_

**[confident]** 我们当时的设计是，Leaf 块是文档的最终切分单元，所以直接把它写入向量库，这样检索效率最高。Root 块呢，其实只是逻辑上的分组，不实际存储，只在检索时通过 Leaf 的 metadata 动态生成。具体来说，Milvus 里每个 Leaf 都带一个 root_id 字段，检索命中后，我们直接从向量库里把同 root_id 的所有 Leaf 都拉出来，拼成一个大上下文。这样就不用额外查 PostgreSQL 了，减少一次 IO，延迟更低。我们实测下来，这个方案比传统父子块回填快了很多，而且效果也不差。

判定：\_\_ok\_\_

## C1 · 幻觉控制（jd）

**题**：面向企业私有知识库的 RAG 应用，你会如何控制大模型的幻觉问题？请从检索、生成、评估三个环节展开。

**要点**：检索环节：通过混合检索（dense+sparse）、重排序、父子分块、查询改写和置信度触发二次检索来提升召回质量，减少幻觉源头。；生成环节：限制上下文、引用溯源、prompt 约束和温度调参，必要时用受控生成或模型选择降低幻觉。；评估环节：建立文档级/页面级召回率和引用命中率等指标，结合自动评估和人工抽检，持续迭代。；结合项目经验：提及自己的 RAG 平台中具体实践，如 Leaf-only 检索、RRF、CrossEncoder 和 Deep Mode。；有取舍：说明不同环节的优先级和成本，如重排序的延迟影响。

**[good]** 我们在做企业知识库 RAG 平台时，幻觉控制是从检索、生成和评估三个环节一起做的。检索上，我们用了 Root+Leaf 的分块，只把叶子块放到 Milvus 里，但检索命中后会把父块的内容回填给大模型，这样既保证精准召回，又给足上下文。同时我们做了 dense 和 BM25 的混合检索，用 RRF 融合，再用 CrossEncoder 重排，这样能先把相关的东西捞全，再把不相关的压下去。另外，我们有个 QueryPlan 模块，会去解析用户问题里的型号、章节这些线索，如果初始检索的置信度不高，就触发 Step-Back 或者 HyDE 做查询改写，再二次召回。生成方面，我们会限定大模型只能基于检索回来的上下文回答，并且要求回答里带上引用来源，prompt 里明确说没有依据就直说不知道。温度一般调低一点，0.1 左右。评估上，我们建了一套万级数据的评测集，看文档级召回率、页面级召回率和引用命中率，文档级能到 99%，页面级 77%，引用命中 70% 多。每次改动都会跑这套评测，再人工抽检一些 case，发现问题再回头调检索或 prompt。不过也得注意成本，重排序和二次检索会增加延迟，所以我们分质量档和轻量档，默认用 FP16 的 CrossEncoder，保证 P50 在 1 秒左右。

判定：ok\_\_\_\_

**[confident]** 控制幻觉的关键是检索要准。我们项目里用了父子分块，把父块存入 Milvus，子块用于检索，这样检索时先找到父块，再返回子块，能提高精度。生成时，我们强制模型只使用检索到的内容，并且设置了很低的 temperature。评估上，我们主要看 BLEU 和 ROUGE 分数，确保生成和原文一致。这样就能有效控制幻觉。

判定：\_\_ok\_\_
